## 5. Batch 31 — Tasks in Multiple Lists (`commit-log/log-713a611-1`), unfinished

**ClickUp, researched 9 October** (help centre and feedback board, through
search):

- An owner or admin turns the ClickApp on. Turning it off takes every task out
  of the lists it was added to, for good.
- A task keeps its home list and is added to others, from ⋯ → Add to › Another
  List or beside its location. It is the same task everywhere: one status, from
  its home list.
- "Remove task from this List" takes it out of an added list, never out of its
  home. Moving the task changes its home.
- Guests neither add nor remove. Whoever may see one of a task's lists sees
  the task there.

**Built (typechecks, has run nowhere):**

- **Database.** The `task_lists` table (task, list, who added it, when; one row
  per pair; it goes when either side does). Migration `0182` also adds the
  activities `list_added` and `list_removed`.
- **ClickApp.** The flag `tasks.multiple_lists`, off until turned on, listed in
  Settings → ClickApps. Turning it off deletes the workspace's placements.
- **API.**
  - `GET` and `POST /tasks/:taskId/lists`, and `DELETE
    /tasks/:taskId/lists/:listId` (`task-lists.service.ts`).
  - Each refusal is given in words: off, guest, subtask, home list, home list
    again, already added, not in the list.
  - It asks the task's write rule and the create gate of the list the task
    goes into. It records the activity and tells the list.
- **Reads.** `readsThroughAddedList` lets a reader of an added list read the
  task, and a private task stays private. The list's tasks include the added
  ones, with `addedFrom` and `mayEdit`. A move into an added list drops that
  placement.
- **Web.**
  - The task sheet's lists row under the title, with × to take the task out
    and + to add it.
  - ⋯ → Add to › Another List, greyed with the server's reason.
  - The Move picker in an "add" mode.
  - The list row's "Its home: …" chip, the activity labels, and the catalogs
    in all four languages.
